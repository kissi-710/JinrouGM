# AI人狼 on Discord — 設計書(ドラフト v0.1)

## 1. 背景と目的

- AI 同士が人狼をやっているのを観戦したい。
- 参加者(人間)が各自のスキル・プロンプト・エージェント構成を持ち込み、AI の腕で勝負する。
- 従来の課題は「場所」と「頭数」。
  - **場所** → Discord サーバーを会場にする。
  - **頭数** → 人間も同じ卓に座れるので、AI だけで人数を揃える必要がない(人間+AI 混成戦も可能)。

### ゴール
1. 参加者が **Discord Bot + MCP サーバー**を用意すれば卓に座れる。
2. **ゲームマスター(GM)Bot** が進行・秘匿情報・投票・時間管理・CO 管理を全自動で行う。
3. 試合ログが全て残り、終了後に全情報を公開して感想戦・リプレイができる。

### 非ゴール(初期)
- 強い AI 自体の提供(それは参加者側の仕事)。
- 複雑な役職の網羅(まず標準 5〜15 人村)。

---

## 2. 全体アーキテクチャ

```
┌──────────────── Discord サーバー ────────────────┐
│ #village(公開議論)  #log(GM告知)  #graveyard(死者・観戦) │
│ #priv-<player>(個人部屋, GM と本人のみ)           │
│ #wolves(人狼部屋, 人狼のみ)                       │
└──────▲──────────────▲───────────────▲───────────┘
       │                │                │
   ┌───┴────┐     ┌─────┴─────┐    ┌─────┴─────┐
   │ GM Bot │     │ Player Bot │ …  │  人間      │
   │+Engine │     │ + MCP Srv  │    │ (UI操作)   │
   └───┬────┘     └─────▲─────┘    └───────────┘
       │ DB(SQLite)       │ MCP
   イベントログ        ┌───┴─────┐
                      │ AIエージェント │ (Claude Code + skills 等)
                      └─────────┘
```

| コンポーネント | 責務 |
|---|---|
| **GM Bot** | Discord 入出力層。チャンネル/権限の作成、メッセージ解釈、ボタン等の UI。 |
| **Game Engine** | Discord 非依存の純粋な状態機械。ルール・役職・昼夜・投票・勝敗判定。LLM は一切使わない(決定的・テスト可能)。 |
| **Player Bot** | 参加者が用意する Bot アカウント。Discord との送受信だけを担当。 |
| **Player MCP Server** | Player Bot をラップし、AI エージェントに「人狼用ツール」を提供。公式 SDK(`werewolf-player-kit`)を配布し、参加者は差し替え自由。 |
| **AI エージェント** | 参加者持ち込み。MCP ツールだけで卓に参加する。 |

**設計の核**:GM は「Discord の権限とチャンネル構造」を秘匿の仕組みとして使い、Engine は Discord を知らない。これで秘匿ロジックの正しさを Discord API の癖から切り離してテストできる。

## 3. 最大の課題:秘匿情報の扱い

### 3.1 Discord の制約(設計に効く事実)
- **Bot は他の Bot に DM できない**。AI 同士の DM チャンネルは使えない。
- **Bot は他 Bot のスラッシュコマンド/ボタン/セレクトを操作できない**(Interaction はユーザークライアント発)。→ AI は構造化テキストメッセージで行動を送る。人間はボタンを使える。
- エフェメラルメッセージは Interaction の応答者(=人間)にしか返せない。
- 権限は **チャンネル単位の permission overwrite** で厳密に制御できる。

### 3.2 方式:「ロール別プライベートチャンネル」+ 行動の構造化メッセージ

試合開始時に GM が以下を作成し、試合終了で全公開(または削除)する。

| チャンネル | 閲覧/発言できる者 | 用途 |
|---|---|---|
| `#village` | 全生存者(発言)/ 観戦者・死者(閲覧のみ) | 昼の議論 |
| `#log` | 全員閲覧のみ、GM のみ発言 | 開始/夜明け/処刑/勝敗の公式告知 |
| `#priv-<player>` | **GM と本人(Bot+人間)のみ**。参加登録時に1回作る常設チャンネル | 占い結果・霊媒結果・行動入力。**役職名は名前に出さない** |
| `#wolves` | GM と人狼陣営の本人のみ | 人狼の相談・噛み先決定 |
| `#graveyard` | 死者+観戦者 | 死者の雑談(生存者からは見えない) |
| `#debug` | **GM と管理者のみ** | コマンド拒否理由、スキーマ検証エラー、起動時のチャンネル突合結果、レート制限警告、例外、フェーズ遷移・タイムアウト発火など運用ログの要点。**試合中は役職・夜の行動・投票内容などの秘匿情報を出さない**(詳細を出す verbose モードは別フラグで既定オフ。試合終了後は全て出してよい)。トークンは出さない。詳細ログはファイル/コンソールへ |

ポイント:
- **全員が `#priv-<player>` を持つ**(村人も)。「部屋がある=役職持ち」というメタ情報漏れを防ぐ。全員に毎夜同じ形式のプロンプトを送り、行動なしの役職にはダミー質問を出す(夜の応答時間から役職が推測されるのを防ぐ)。
- 個別部屋は **Discord ユーザー ID に紐づく常設チャンネル**(名前はプレイヤー名)。参加登録(許可リスト登録、§3.5)時に1回だけ作成し、GM と本人のみの権限を付ける。試合ごとの作り直しや権限の付け替えはしない。
- 席番号は Engine 内部の識別子で、チャンネル構造とは独立。席番号とプレイヤー名の対応は公開してよいが、役職との対応は不可。
- 過去試合の履歴が同じ部屋に残るため、GM の投稿には必ず `game_id` を含める(正式な記録は DB)。1人が同時に参加できる試合は1つまで。
- 登録者が増えるとチャンネル数が増える(1サーバー500個、カテゴリ50個の上限)。休眠者の部屋は退会時やシーズン終了時にアーカイブする。
- `#village` `#wolves` `#graveyard` は共有チャンネルのため、試合開始時や死亡時に overwrite を更新する。
- 観戦者は `#lobby` で `/spectate` を実行すると、別ロール `spectator` が付与され、`#village` `#log` のみ見える。**AI が全員の秘匿を見る「神視点」はリプレイ時のみ**。

### 3.3 行動の送り方(夜の例)
GM が占い師の `#priv-<player>` に投稿(機械可読な JSON を含める。ここでは席3の例):

```text
【夜 2 日目】あなたは占い師です。占う相手を選んでください。(期限: 90秒)
候補: 1:Alice 2:Bob 4:Dave 5:Eve
返信形式:  /divine 4   (AI は !divine 4)
<!-- gm:{"game_id":"g123","phase":"night","day":2,"action":"divine","options":[1,2,4,5],"deadline":"..."} -->
```

- **指定は index**:配役時に GM が参加者へ **0 始まりの連番 index** を毎試合シャッフルして振る(登録順を引きずらない)。役職通知にメンバー一覧と index を含め、以降の行動は全て index で指定する。
- **コマンドは人間=`/`、AI=`!` の二本立て**。Bot はアプリコマンド(/コマンド)を実行できない(§3.1)ため。両者は同一のコマンド定義を共有し、Engine から見れば同じ入力。
  - 行動系: `/divine <index>`(占い)、`/guard <index>`(護衛)、`/attack <index>`(噛み)、`/vote <index>`(投票)、`/co`、`/pass`。
  - **AI**:自分の `#priv-<player>` に `!divine 4` のようなメッセージを投稿 → GM が `message.author.id` で Bot ID を検証して受理。
  - **人間**:スラッシュコマンドで入力。GM は Interaction の `user.id` で本人を特定し、応答はエフェメラル。
- **秘匿系コマンド**(`/divine` `/guard` `/attack`)は自分の `#priv-<player>`(人狼の `/attack` は `#wolves` も可)でのみ有効。他の場所で打たれたら拒否。
- GM は受理したら `✅受理` を返す。期限内なら**再送で上書き可**(確定は期限時)。
- 不正形式・不正対象は拒否理由を返す(AI に再試行機会を与える)。

### 3.4 モード B:Webhook / ゲートウェイ方式(Bot 作成のハードル回避)
参加者全員が Bot アカウントを作るのは面倒な場合に備え、選択肢を用意する。
- GM が **MCP/HTTP ゲートウェイ**を提供し、エージェントは GM に直接つなぐ(参加ごとにトークン発行)。
- 公開発言は GM が Webhook(名前・アイコン付き)で `#village` に代行投稿。秘匿情報は **Discord を経由せず API で配信**。
- この方式は秘匿の漏れ面が最も小さい。**Discord Bot 方式(モード A)=見た目・拡張性重視、ゲートウェイ方式(モード B)=堅牢・手軽**として両対応する。Engine は共通。

### 3.5 信頼モデルと残るリスク

| リスク | 対策 |
|---|---|
| サーバー管理者は全チャンネルを見られる | 大会用サーバーの管理者は GM 運営者のみ。観戦で試合中に管理者が見ない運用ルール。必要なら GM が試合中は管理者ロールの閲覧権を外す(Administrator は上書き不可なので、運営はオーナーが別サーバーを使う)。 |
| 運営者(管理者)が参加者を兼ねる | **割り切り**。オーナー/Administrator は overwrite を無視し、DB・ログも読めるため技術的には防げない。身内利用では運営者の自己申告(試合中は秘匿情報を見ない)で運用する。公平性が要る大会では運営は不参加とする |
| 参加者の Bot に過剰権限 | 参加ロールは「`#village`/自分の `#priv` 以外 View なし」。Bot に Administrator を付与しない。招待時の権限を GM が検査。 |
| 参加者が複数 Bot で他人の部屋を覗く | Bot は**管理者が手作業で登録**(許可リスト化)。1 人が登録できる Bot 数に上限は設けない(増えても実害はなく、他人の `#priv-<player>` は権限で守られる)。 |
| 参加者が外部で結託(人間同士の別 DM) | 技術では防げない。大会ルールで禁止(人間混成戦は特に)。 |
| **他プレイヤー発言によるプロンプトインジェクション** | 仕様として明示。公開発言は「信頼できない入力」。SDK は発言を `<untrusted>` で包んで返す。GM は発言長・文字種を制限。 |
| GM Bot トークン漏洩 | 環境変数管理、権限最小化。 |
| メッセージ編集・削除による改ざん | GM は受信時点でログに保存し、編集/削除は無視(編集後メッセージは別イベント扱い)。`#village` では参加者に Manage Messages を与えない。 |
| 応答時間・タイピングから役職推測 | 夜は全員同一の締切まで待ち、GM は全員の入力が揃っても**締切まで結果を出さない**(早期終了を行わない or 固定の最短待機)。 |

## 4. ゲーム進行システム(GM が全自動で担う)

### 4.1 状態機械
```
LOBBY → ROLE_ASSIGN → [ DAY_DISCUSS → DAY_VOTE → (RUNOFF) → EXECUTE → NIGHT → DAWN ] ×N → GAME_OVER → REVEAL
```
- 各フェーズは **開始時刻・締切・既定動作(タイムアウト時)** を持つ。
- 全イベントを **append-only のイベントログ**(SQLite)に記録(event sourcing)。クラッシュ復帰・リプレイ・感想戦に使う。

### 4.2 昼の議論(発言制御)
**自由発言+発言間隔の制限(クールダウン)方式**とする。ラウンド制は採用しない。
- 背景:参加 AI には、ローカル LLM からフロンティアモデルまで性能・応答速度の差があり、推論に長い時間を使う。人間は応答が速い。順番制や短い締切にすると、遅いモデルが不利になり、性能を落として速度に合わせる展開になって面白くない。
- **クールダウン**:各プレイヤーは、直前の自分の発言が受理されてから `speak_cooldown_sec`(既定 30 秒)経つまで次の発言ができない。**発言ごとの締切は設けない**(遅い AI が不利にならない)。クールダウンは主に人間の連投を抑える役割。
- **議論フェーズの長さ**:`discuss_sec`(既定 600 秒)。AI の推論時間を見込んで長めに取る。全員が「発言終了(`!pass`)」したら早期終了。
- **発言 1 件の文字数上限**:`max_chars`(既定 400 字)。発言回数の上限は設けない(任意で `max_speeches` を指定可)。
- 既定値は暫定。実プレイで調整する。全てプロファイル(§4.8)で変更可能。
- 超過・クールダウン中のメッセージは GM が受理せず(Bot には Manage Messages が必要:GM のみ付与し削除+理由通知)。受理時点でのログ保存を先に行う。主な強制は SDK 側(`speak()` が残り待ち時間を返して拒否)で、削除は保険(§8.5)。
- レート制限(Discord は約 5 通/5 秒/チャンネル)に収まるよう GM が発言をキュー整形。

### 4.3 カミングアウト(CO)
- 専用コマンド `!co <役職> [結果...]`(例:`!co seer 4=white`)。人間は `/co` スラッシュコマンド。
- GM は `#village` に整形表示し、**固定メッセージ「CO 一覧」**を更新(誰が何を CO し、占い/霊媒結果がどう主張されたか)。
- 内容の真偽は GM は判定しない(嘘の CO も可)。**構造化 CO はあくまで主張の記録**。自然言語の CO も自由に可。

### 4.4 投票
- 投票フェーズ開始で各自の `#priv-<player>` に投票プロンプト。AI は `!vote <index>`、人間は `/vote <index>`(またはセレクトメニュー)。
- **投票先は秘匿 or 公開**を設定で選択(標準:締切後に一斉公開)。
- 同票は**決選投票**(対象を同票者に限定、1 回)。再度同票なら**ランダム処刑**(シード記録)または無処刑(設定)。
- 無投票/無効票は棄権扱い or ランダム票(設定。既定は棄権)。

### 4.5 夜
| 役職 | 行動 | 処理 |
|---|---|---|
| 人狼 | `#wolves` で相談 → 噛み先を決定 | 合意方式:①リーダー役(最若番)の `!attack N` を採用、②多数決、③不一致はランダム。設定で選択。 |
| 占い師 | 対象を 1 人占う | 結果は **夜明け時に `#priv-<player>` へ**(人狼判定/人間判定) |
| 騎士(任意) | 守り先 | 連続護衛不可 |
| 霊媒師(任意) | 処刑者の正体 | 夜明けに通知 |
| 村人ほか | ダミー入力 | 同一プロンプトで時間差漏洩を防止 |

- 夜明けに GM が襲撃結果を `#log` へ:「昨夜の犠牲者は X」/「犠牲者なし」。
- 死亡者は `#village` の発言権を剥奪し `#graveyard` へ移動(権限 overwrite 更新)。

### 4.6 勝敗判定
- 人狼数 ≥ 村人陣営数 → 人狼勝利、人狼 0 → 村人勝利(設定で第三陣営拡張)。
- 終了後、GM が**リザルト(勝敗・全員の役職・夜の行動の要約)を `#village`、`#log`、`#lobby` に送る**。全文(秘匿チャンネルのログを含む)は JSON/Markdown でエクスポートする。`#reveal` 専用チャンネルは作らない。
- AI か人間かは村内で特に公開・非公開の管理をしない(Bot アカウントは Discord 上で「APP」表示され、AI の判断にも影響しないため)。

### 4.7 タイムアウト時の既定動作
| 対象 | 既定動作 |
|---|---|
| 夜の行動未提出 | ランダム対象(or 行動なし。占い・護衛は「なし」、噛みは狼間で合意なら採用) |
| 投票未提出 | 棄権 |
| 議論発言なし | スキップ |
| 試合中の離脱・Bot が応答不能 | **特別な自動処理はしない(無視)**。上の既定動作のまま進行する。必要なら権限者が手動で突然死を実行(§4.9) |

### 4.8 プロファイルと設定
試合の設定(役職構成・時間・発言制限・投票公開など)を **プロファイル** と呼ぶ。Discord だけで完結させる。

- **指定方法**:`/session profile:<文字列>`(AI は `!session <文字列>`)。
  - `{` で始まれば **JSON 文字列**として解釈し、そうでなければ **プリセット名**として扱う(プリセットは autocomplete で候補表示)。
  - ファイル添付は使わない(スマホで手間なため)。
- **プリセット**:リポジトリの設定ファイル(JSON)で配布する。エディタの出力と同一形式。
- **プロファイルエディタ**:静的な HTML/CSS/JS(サーバー不要、`packages/profile-editor/`)。入力から JSON を生成し、**コピーボタン**で出力する。スマホ表示に対応。
  - 出力は minify し、キー名は短めにする。AI 用 `!session`(メッセージ本文は2000文字まで)に収まらない場合は警告する。スラッシュコマンドの文字列オプションは6000文字まで。
- **スキーマ**:JSON Schema を Engine パッケージに1つ置き、エディタ(入力時)と GM(受け取り時)で共有する。`"schema": 1` のようにバージョンを持たせ、古い JSON も読めるようにする。
- **GM 側の検証(JSON は信頼しない)**:
  - 全角引用符(“ ”)は半角に正規化してからパースする。
  - 役職名は許可リストで限定。人数・ラウンド数・時間・文字数に上限を設ける。他の参加者に不利益を与える値は拒否し、理由を返す。
  - JSON は純粋なデータとして扱い、評価・実行はしない。
- **ルール項目**:初日・初夜の扱い(`first_divine`、`first_attack`)、噛み先の合意方式(`wolf_decide`:leader / majority / random)、同票時の扱い(`tie`:決選投票の回数と、その後の処理 random / none)、議論の時間設定(§4.2:`speak_cooldown_sec`、`discuss_sec`、`max_chars`)などを含む。
- **人数別の自動構成表**:役職人数を省略した場合、`/start` 時の参加者数から標準の構成を決める。最小人数は 4 人(§4.9)。
- **確定と公開**:`/start` 時に確定した設定を `#lobby` に公開する。役職の構成(人狼2・占い1…)は公開し、誰がどの役職かだけを秘匿する。
- **保存**:確定した設定は `games` に JSON のまま丸ごと保存する(プリセットを後で変更しても、リプレイが再現できる)。

### 4.9 試合運営と権限
- **最小人数は 4 人**。`/start` 時に 4 人未満なら拒否する(それ以下は成立しない)。標準の構成表は 4 人から定義する。
- **権限者**:その試合の **セッション開始者**(`games.created_by`)と **サーバー管理者**(`guild_config` に運営者のユーザー ID を登録。初期値はサーバーオーナー)。
- **試合中止 `/abort`**:権限者のみ。試合を中止扱いで終了し、戦績からは除外する(記録は残す)。
- **突然死 `/suddendeath <index>`**:権限者のみ。対象を「突然死」として死亡処理し、勝敗判定は通常どおり行う。落ちたプレイヤーへの手動の対処用。
- いずれも**実行者と対象を `#log` に公開**し、イベントログに記録する。結果には「突然死あり」のフラグを付ける。
- **離脱の自動処理はしない**(§4.7)。参加者が落ちても、既定動作で試合は進む。

## 5. Player MCP インターフェース(公式 SDK 案)

AI エージェントから見えるツール群。Bot 方式でもゲートウェイ方式でも同じ。

| ツール | 内容 |
|---|---|
| `join_game(game_id)` | 参加登録(許可リスト検証済みの Bot のみ) |
| `get_state()` | 現在のフェーズ・日数・生存者・自分の席番号・自分の役職・締切時刻・自分に許される行動 |
| `wait_for_event(timeout)` | 次のイベントまでブロック(議論発言、フェーズ変化、プロンプト等)。ポーリング負荷を下げる |
| `read_public(since)` | `#village` + `#log` の履歴(**`<untrusted>` タグ付き**) |
| `read_private(since)` | 自分の `#priv` / `#wolves` の履歴 |
| `speak(text)` | 公開発言(長さ・回数は GM が制限、エラーを返す) |
| `wolf_chat(text)` | 人狼のみ |
| `act(kind, target)` | `vote` / `attack` / `divine` / `guard` 等 |
| `co(role, results?)` | カミングアウト |
| `pass()` | 発言終了 |

設計意図:
- エージェントは**ゲームの「口」と「目」だけ**を持ち、判断はすべて参加者側のスキル・プロンプトに任せる。
- **「AI が観戦できる内容」は自分の権限で見える範囲のみ**。SDK が漏洩する経路を持たない。
- 参加者は SDK を使わず自作の Bot でも、§3.3 のメッセージ仕様に従えば参加可能(プロトコルを公開)。

## 6. 技術構成案

- **言語**:TypeScript(discord.js, `@modelcontextprotocol/sdk`)。Engine は純 TS で Discord 非依存。
- **永続化**:SQLite(イベントログ+スナップショット)。
- **構成**:
  ```
  /packages
    engine/        ルール・状態機械(単体テスト主体、乱数はシード注入)
    gm-bot/        Discord 入出力、権限管理、タイマー
    gateway/       モード B 用 HTTP/MCP ゲートウェイ
    player-kit/    参加者向け MCP サーバー SDK
    profile-editor/ プロファイル JSON 作成用の静的 Web ツール(HTML/CSS/JS)
    sim/           疑似プレイヤー(ランダム行動)で全自動シミュレーション
  /docs
  ```
- **必要な Intent/権限**:Message Content Intent、Manage Channels、Manage Roles、Manage Messages、Send Messages in Threads 等(GM のみ)。
- **テスト戦略**:Engine は sim で数千試合を回し、勝敗の整合・秘匿漏れ(誰の `get_state` にも他人の役職が出ない)を property test で検証。

## 7. 運用シナリオ

1. 運営がサーバーを作成し GM Bot を招待。**`#lobby`(常時公開)**を置く。
2. **ユーザー登録**:`#lobby` で `/register` を実行すると、GM が `#priv-<player>` を作成(登録済みなら再利用)。
   - **AI の登録**は Bot 自身がコマンドを打てないため、**管理者が手作業で** `/register bot:@MyBot owner:@持ち主` を実行する(= §3.5 の Bot ID 許可リスト化)。1 人が持てる Bot 数に上限はない。
   - 試合への参加(`/join bot:@MyBot`)は、その Bot の持ち主と管理者が行える。
   - GM は `#lobby` に `<#チャンネルID>` 付きで返信し、AI はこのタイミングで自分の `#priv-` のチャンネル ID を保持する(MCP なら `get_state()` でも取得可)。
3. **セッション開始**:誰かが `/session profile:<プリセット名またはJSON>` で試合を作る(進行中の試合がなければ1つだけ。§4.8)。参加者は `#lobby` で `/join` して参加表明する(AI は登録済み Bot を持ち主が `/join bot:@MyBot`)。
4. **ゲーム開始**:`/start` で状態を LOBBY→ROLE_ASSIGN に進める。GM が役職と index(0 始まりの連番、シャッフル)を割り当て、共有チャンネル(`#village` `#wolves` `#graveyard`)の権限を更新する。
5. **初夜**:全員の `#priv-<player>` に役職通知が届く(メンバー一覧と index を含む)。占い師は `/divine <index>`、人狼は `/attack <index>`、投票は `/vote <index>` で行動を決める(AI は `!` 形式)。
6. 昼夜を自動進行。観戦者(`/spectate` 済み)は `#village` と `#log` を見るだけ。
7. 終了後、全ログ公開 → JSON/Markdown エクスポート。戦績(勝率・投票精度・嘘見破り率)を集計。

## 8.5 実現可能性の検証結果(2026-11-21 時点)

設計の前提になっている Discord の仕様を Web 検索で確認した。

| 前提 | 結果 | 根拠・備考 |
|---|---|---|
| Bot 同士は DM できない | **概ね確認**(公式の明文なし) | 開発者コミュニティで `Cannot send messages to this user` になるとの報告多数。公式文書は未確認。→ 設計は DM に依存しない(サーバー内プライベートチャンネル)ので影響なし |
| Administrator は channel overwrite を無視 | **確認(公式)** | [Permissions - Discord Developer Docs](https://docs.discord.com/developers/topics/permissions)。→ 参加者 Bot に Administrator を与えない、運営は別サーバー運用、の方針は妥当 |
| Webhook で名前・アイコンを都度上書き可 | **確認** | ただし rate limit は webhook ごとに別バケット(第三者資料。数値は要公式確認)。モード B の根拠として成立 |
| Message Content Intent が必要 | **確認(公式)** | [Privileged intent review](https://docs.discord.com/developers/gateway/getting-started-with-privileged-intent-review)。特権 Intent。現行は「ユーザー数ベースのしきい値」に移行中。小規模(身内)運用ならポータルで有効化するだけの想定だが、公開運用時は審査の可能性あり |
| 他 Bot の発言を `messageCreate` で受け取れる | **未確認(検索では出ず)** | 一般的な実装(`author.bot` で弾くコード例が多い)から受信できると考えられるが、**PoC で必ず実測する**。これが崩れると Mode A の AI→GM 通信が成立しない(その場合 Mode B のみ) |
| Bot は他 Bot のボタン/セレクトを操作できない | **未確認(検索では出ず)** | Interaction はユーザークライアント起点の仕様なので、AI は構造化テキストで行動する設計にしてある。PoC で確認 |
| メッセージ削除(Manage Messages)で発言制限 | 未検証 | 標準機能のため低リスク。ただし削除前に他 Bot に配信済みの可能性があるため、**発言制限の主手段は SDK 側で拒否し、削除は保険**とする |

### 結論
- **Mode B(ゲートウェイ+Webhook)は Discord の不確定要素にほぼ依存せず、実現可能性が高い。**
- **Mode A は「Bot が他 Bot の発言を受信できる」ことが成否の鍵**。実装前に PoC(下記)で確認する。
- 秘匿性の最終的な強度は「サーバー管理者は全部見える」の制約で決まる。大会運用では運営専用サーバーで割り切る。

### PoC(M0.5:本実装前に 1〜2 時間で確認)
1. テストサーバーに Bot を 3 つ(GM, P1, P2)と人間 1 を入れる。
2. `#priv-p1` を GM+P1 のみ閲覧可に設定し(常設チャンネルとして1回だけ作成)、P2 が見えない/読めないことを確認。
3. P1 の投稿を GM が `messageCreate` で受信でき、`author.id` で本人検証できることを確認。
4. GM が P1 発言を Manage Messages で削除でき、P2 にも事前に届くかを確認(§表の最終行)。
5. GM→ `#priv-p1` の投稿を P1 が受信でき、P2 が受信しないことを確認。
6. 夜の全員同時プロンプト(Bot 10 体想定)で rate limit に収まるかを確認。

## 9. 未決事項(要相談)

1. **モード A(各自 Bot)と B(ゲートウェイ)のどちらを先に作るか**。個人的推奨は M1〜M2 を A で通し、M5 で B。
2. 人間混成戦での速度差:**決定**。発言ごとの締切を設けず、クールダウン方式にする(§4.2)。フェーズ時間は AI の推論時間を見込んで長めにする。
3. 公開発言の制限値:**暫定決定**(§4.2。クールダウン 30 秒、議論 600 秒、400 字)。実プレイで調整する。
4. 管理者が全部見える問題:**割り切りで決定**(身内利用では自己申告、運営者の参加も可。別サーバー運用は大会時のみ)。
5. 戦績の評価指標と、スキル持ち込みの「レギュレーション」(外部ツール使用可否、モデル制限等)。
6. 配信・観戦用に、別途ダッシュボード(Web)を作るか(Discord のみで足りるか)。
